## 1. Launch and prompt

- **R1 Prompt delivery** (RC C1/C2, RF S2): launch.md §2.2-2.3 is the design. No user text ever enters argv. Source of truth = `prompts/<job id>.md` (managed by the plugin). At fire time the host writes the snapshot `runs/<job id>/<run id>/prompt.md` and passes `@<snapshot>` plus the fixed positional `Run the scheduled job described in the attached file.` Delete engine.md's "prompt after `--`" form and the claim "no shell quoting" (Tern joins argv into a `/bin/zsh -l -c` string, PR2 T4). `prompt_source="file"`/`prompt_path` are **cut from v1** (RF S3c: arbitrary-file read; RP P9 list).
- **R2 Run directory**: `runs/<job id>/<run id>/{prompt.md, preamble.md, omp.yml, session/}`; `--session-dir <run>/session`. The ledger moves to `ledger/<job id>.jsonl`. Correlation key = the `/runs/<job id>/<run id>/` substring in the pane's command.
- **R3 Ids**: job id `j_` + 8 `[a-z0-9]`; run id deterministic `r_<job8>_<slot>` for scheduled/catch-up slots, `r_<job8>_<epoch>_<rand4>` for manual runs (engine D2 wins). Daemon `block`/`tab`/`session` ids are stored as **strings** extracted with a pattern from `tern new --json` stdout, and passed to window APIs as-is.
- **R4 Binaries**: launch.md §1 order (Tern-managed omp first; validate with `--version`). No bare-`omp` fallback: missing omp ⇒ run `blocked/omp_missing`.
- **R5 Pane lifetime**: every launch passes `--keep-open`; the host alone closes run panes. **M1 ships a global cap: keep at most 5 finished run panes**; the oldest finished, unfocused run pane is closed with `tern close` after its facts are persisted (RP P8, RF F9: an idle omp is 113-525 MB). Job default `after = keep` (subject to the cap); `close_ok` and `close` stay as options.
- **R6 Preamble**: launch.md §3 text via `--append-system-prompt <run>/preamble.md` (V6; fallback: prepend it to the snapshot). Always on in M1 (the per-job toggle is deferred). It asks for a final `RESULT:` line. Summary = last `RESULT:` line, else first line of the last message. `RESULT: FAILED - …` ⇒ `failed/agent_failed`. Quiet success (`[quiet]`, `quiet_ok`) is **deferred** past M1.
- **R7 Safety overlay** (RF S4): every non-yolo run passes `--config <run>/omp.yml` pinning `tools.approval` of exec-tier tools to `prompt` so a repo's `.omp/config.yml` cannot widen "Ask before commands" (verify precedence, new V-item). User-global extensions still load (e.g. omp-pushover is useful for scheduled runs); project-level extension risk is documented, not blocked, in v1.
- **R8 Notifications** (RF S5, RP P5): the **host** sends every OS notification (single writer, deduped), via argv-passing osascript only: `{"/usr/bin/osascript","-e","on run argv","-e","display notification (item 1 of argv) with title (item 2 of argv)","-e","end run", text, title}`, text/title stripped of control chars, ≤200 chars. Toasts are window-side. Copy must state: with no Tern window open, a run that stops for approval waits silently until a window opens or its time limit hits; host-visible failures (launch failure, early exit, timeout, blocked) still notify.

## 2. Engine, states, transport

- **R9 Observation** (RC C12-C15): windows send **raw** agent samples; the **host** owns debouncing and every transition (engine constants). A window writes an `obs` intent on change **and** a heartbeat every ≤30 s while a run's state persists. `last_message` is truncated to 4 KiB in intents (RF F4); full text and cost come from the session JSONL read asynchronously on the host via `/usr/bin/tail -c 1048576` through `tern.process.run` (never a large synchronous `tern.fs.read`; RF F9); cost is labeled approximate when truncated.
- **R10 Intent protocol + security** (RF S1): envelope `{format:1, kind, ...}`, file name `<t_ms>-<win8>-<seq>.json`, applied in name order, undecodable retried for 60 s then dropped. **Allowlisted kinds only**: `obs`, `run_now` (existing job id; runs with stored settings), `pause`, `resume`, `pause_all`, `resume_all`, `stop_run`, `focus_run`, `open_run`, `roles_request`, `ack_failed`. **No `create`/`update`/`delete`/`settings` intents.** Creating and editing jobs and settings happens only inside the host manager block; palette "New job" and any future Carly `job_add` open the manager with draft args via `cx:new_block` (new M1 gate V-item). Intent payloads are validated by the same validator as the form. Hands-off approval is bound to a hash of (prompt text, cwd, role): a hands-off job whose hash no longer matches is `blocked/hands_off_review` until re-confirmed in the manager (RF S3). Document plainly: plugin data is not a security boundary against processes running as the user.
- **R11 kv**: holds only the host-written `hot` key (rev, counters, heartbeat). Windows never write kv. First-run flags, binary paths and role cache live in host files (`settings.json`, `cache.json`).
- **R12 Run states**: engine.md machine states are canonical (`scheduled launching running needs_input finished failed timed_out cancelled skipped missed blocked`). ux.md shows UI labels through one mapping table: starting=`launching`; queued=`scheduled` waiting on cap or overlap queue; needs you=`needs_input`; ok=`finished`; stopped=`cancelled/user_stop`; caught up = any run with `trigger=catchup`. A too-late slot is `missed` with the sentence "Missed Mon 09:00: 13h late, over the 3h limit." (no `skipped(late)`). "Prompt not delivered" (no `working` within 180 s) is `failed/no_response`, counts toward the streak, pane kept. Block gone without our close: `failed/interrupted` if a daemon/heartbeat gap precedes it, else `cancelled/closed_by_user`. Daemon restart can restore a pane as a login shell (RF F5): liveness requires the run-id substring in the pane's command.
- **R13 Glyphs**: needs you `⚠`; blocked uses the `shield-alert` icon; failed/timed out `✗`; stopped neutral `■`; skipped `↷`; missed `◌`; ok `✓`; caught-up runs show `✓` + "caught up"; test/manual runs get a text suffix only.
- **R14 Tern state reads**: one helper over `tern ls --json` for sessions, blocks and liveness (`panes[].live` from `inspect` does not exist, RF F8). `tern inspect --json` only where a field exists only there.
- **R15 Constants**: host tick 15 s (due check + liveness while runs are in flight); single-flight FIFO launch queue; window observer every 3 s while the snapshot lists in-flight runs, heartbeat 30 s; status segment refresh ≤ 1/min unless state changes. Window half uses tern-swarm's staged module loader (RF F7).

## 3. Product

- **R16 Role**: stored bare (`default`), displayed and passed as `@default`; the default for new jobs is `@default` (literal requirement). Example jobs explicitly use `@smol` with their cost shown. "Other model…" (pinned model id) is **cut from v1**. Roles are read per job cwd; if the role list can't be read, the run proceeds and records `role_unverified`; if it was read and the role is absent, the run is `blocked/role_missing`.
- **R17 Working directory** (RP P12): no `$HOME` fallback. The Folder row is pre-filled from the focused local pane's cwd; otherwise empty and required ("Pick a project folder."). Explicitly picking `~` stores `allow_home = true` (passes `--allow-home`) with omp's temp-dir caveat. Paths with `' " \ $ \`` ! newline` are rejected at save with copy "Folders with quotes, $ or ! in the name aren't supported yet."
- **R18 Approval**: default "Ask before commands" (`write`) **pending the user's decision (Q1)**. "Read-only" is hidden until its tool allowlist is verified (V9). Example jobs must work under their stated approval mode (RP P2): no example may need a shell under Read-only.
- **R19 Catch-up**: default `within` 3 h (pending Q2), and "If your Mac was asleep" becomes a visible row in the main form section, not Advanced (RP P6). No example is scheduled at a time a laptop is usually asleep.
- **R20 Availability copy** (RP P1, RF F2): "Jobs run while Tern's session service is running. It keeps running after you close windows as long as a terminal or run is still open. Nothing runs while your Mac is asleep, or after a restart until you open Tern." Setup check adds a "Keep-alive" row reading `tern ls --json`. Real-daemon lifetime with zero windows is a gating V-item.
- **R21 Multi-window** (RP P4, RF F1): `tern` CLI acts on "one window's sessions… else the first window", and the plugin cannot read `TERN_WINDOW_KEY` (PR2 T7). Gating V-item: with two windows, are sessions daemon-wide (expected) or per window? If per window, runs land in the first window; the doc says so.
- **R22 Naming** (RP P7): the run session default name is **"Scheduled runs"** (setting). Palette group and manager tab stay "Schedule".
- **R23 M1 = minimum lovable loop** (RP P3, §4.2): create → it fires → I see it ran / needs me / failed → I open the result.
  - **M1**: engine as specified; launcher with placements *Scheduled runs session* (default) and *Background tab in the current session* + *Bring to front* switch; minimal observer (needs you / finished / failed / last message); status segment (stalled/setup, needs you, failed, running, next); toasts; host OS notifications; Open run (focus or `--resume`); run history with reasons; pane cap; manager List (Needs you, Running, Upcoming, Paused & finished) + Detail + a 9-row form (Name, Prompt, When with live preview, If your Mac was asleep, Folder, Role, Approval, Stop after, Active); actions Run now, Pause/Resume, Delete (two-press + undo), Duplicate, Pause all; palette Open manager, New job, Run a job now, Go to run that needs me; Setup check; empty state with examples; first-run "Run now and watch" overlay.
  - **M1 gate (spike first)**: palette → `cx:new_block` opens the host manager with draft args; multi-line text editing in a host block (swarm `textfield`); `prefs` inside a host block. If multi-line editing misses its time box, ship a one-line prompt field + `ctrl+o` to open `prompts/<id>.md` in Tern's doc editor.
  - **M2**: split and picture-in-picture placements (after V10/V11), tab badges, Interrupt (keep pane), Recent runs and Pause/Stop pickers, per-job notify / after-run / overlap options in an Advanced section, Quick add, filter, quiet success, settings sheet beyond core rows.
  - **M3**: Carly exports (draft-only create), worktree isolation, bundled omp run-reporter extension, "Allowed commands" overlay if not already shipped, export/backup.
- **R24 Install & removal** (RP P14): README covers `tern plugin install`, minimum Tern 0.7.2, what removal leaves behind (`plugin-data/schedule`, run panes), and Settings gets "Open data folder".
- **R25 Discovery**: on first load, one `info` toast "Schedule is ready. Press ctrl+alt+shift+s." (flag in host `settings.json`). First-ever scheduled (non-test) run toasts once.

## 4. Open questions for the user (final list)

1. **Default approval for new jobs**: (A) Ask before commands + per-job "Allowed commands" list (`git`, `gh`, `npm test`…) compiled into the overlay, if omp's `bash` patterns verify — *recommended*; (B) Hands-off by default (matches your omp default `yolo` and tern-swarm); (C) Ask before commands with no allowlist (safe, but most real jobs stall on their first shell command).
2. **Catch-up window**: 3 h (*recommended*), 12 h, any age (Raycast), or skip.
3. **Keeping Tern's service alive**: (A) honest copy + Setup keep-alive row (*recommended*); (B) the plugin keeps one idle pane in the runs session so the service survives closing every window; (C) an opt-in launchd agent that starts `tern daemon` at login.
4. **Finished run panes**: keep with a cap of 5 (*recommended*), close successful runs right away (relies on `--resume`), or keep everything.
5. **Where runs live**: a dedicated "Scheduled runs" session (*recommended*) or background tabs in whatever session you're in.
6. **Form scope for M1**: 9-row in-block form (*recommended*), a palette wizard of `cx:prompt`/`cx:pick` steps, or the full Advanced form from day one.
